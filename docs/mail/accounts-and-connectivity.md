# Accounts and connectivity

## Status

**Implemented foundation with bounded local preflight, opt-in live IMAP/SMTP TLS inspection, an ephemeral OAuth authorization-code/PKCE boundary, a provider-gated Windows token-vault adapter, a mock-only token-lifecycle harness, and an explicit live POP3 account-test transport.** Manual configuration, provider presets, standards-based DNS discovery, deterministic protocol/host/port/security diagnostics, and credential-free local foundations exist. POP3 can now test one entered account over implicit TLS or required STARTTLS, but POP3 account saving, message retrieval, durable UIDL state, polling, deletion, folders, outgoing delivery, and synchronization are not implemented. No provider client ID ships in this build's source; Microsoft sign-in, token exchange, and refresh are implemented and read a client ID from the environment at startup, but no live Microsoft tenant has exercised them yet. Google stays unconfigured, since its authorization request needs access_type=offline handling this build does not have.

## Behavior

Account discovery validates an email address, then combines up to three sources:

- an advisory lookup of the provider domain's `_imaps._tcp` and `_submission._tcp` DNS SRV records with a four-second bound;
- built-in settings for several common domains; and
- a conventional `imap.<domain>` / `smtp.<domain>` suggestion.

The user can review and edit incoming and outgoing host, port, security, username, and authentication mode. Adding an account tests both incoming IMAP and outgoing SMTP connectivity before storing it. The secret is encrypted with Windows-backed `safeStorage`, and renderer-facing account summaries omit it. Removing an account atomically purges its live cache, drafts, outbox records, pending mail operations, and matching open composer; append-only semantic and local-revision history is retained rather than rewritten. Every account-scoped completion rechecks that the account still exists, so a late draft, send, synchronization, folder, or message result cannot recreate purged live state. A fully local demo account is available without a network connection.

### Live POP3 account test

Account setup offers IMAP or POP3 as the incoming protocol. Selecting POP3 switches conventional diagnostics to implicit TLS port `995` and STARTTLS port `110`, fixes authentication to `password`, enables the password and **Test settings** controls, and keeps **Connect account** disabled. The separate certificate-inspection action remains disabled because its STARTTLS dialect covers IMAP/SMTP, not POP3. The visible boundary says that the test contacts only the entered POP3 endpoint and that outgoing SMTP, account saving, retrieval, deletion, polling, and synchronization will not run.

The main-process live client accepts only implicit TLS or STARTTLS; plain POP3 is rejected before a socket opens. Implicit TLS negotiates TLS before the greeting. STARTTLS reads a bounded greeting, runs `CAPA`, requires advertised `STLS`, upgrades the same socket, and runs `CAPA` again inside TLS. Only then may the fixed command allowlist send `USER`, `PASS`, `STAT`, bounded per-message `UIDL n` / `LIST n`, and `QUIT`. At most `1..50` message numbers are sampled. It never sends `RETR`, `TOP`, or `DELE`, never requests a message body, and never starts SMTP.

The default limits are 5 seconds each for TCP/TLS setup, greeting, command response, and multiline body; the whole session is capped at 30 seconds. A response line may use at most 8 KiB; a multiline response may use at most 64 KiB and 512 lines; an outbound command may use at most 17 KiB. Every line must have POP3 CRLF framing. `STAT`, `UIDL`, and `LIST` numbers must be bounded safe integers, sampled UIDLs must be unique printable tokens, and required commands must receive a syntactically valid `+OK`. Cancellation aborts the owning main-process controller, destroys active sockets, clears the single-flight slot, and returns focus to **Test settings**.

The renderer receives only a fixed result shape: transport kind, negotiated protocol/cipher, fixed capability booleans, mailbox message/octet counts, sampled count, and literal boundary facts. Host, username, password, greeting, raw server response text, raw capability arguments, UIDLs, and transcripts never return through IPC. The test does not call `safeStorage`, the account store, history, notifications, IMAP, SMTP, or synchronization. POP3 add remains a main-process refusal, so a successful test still saves nothing.

Password mode retains that reviewed connection path. OAuth mode never accepts a pasted access token: it clears and hides the password field and exposes a separate bilingual browser-foundation panel instead. Testing and account creation stay disabled until a browser sign-in for the selected provider has actually completed and exchanged for a token; the main process enforces the same rule independently of the renderer, so a renderer bypass cannot test or save an OAuth account without one. By default, production reports Google and Microsoft registration as unavailable, because no client ID is configured; setting MATERIAL_EMAIL_MICROSOFT_CLIENT_ID (and optionally MATERIAL_EMAIL_MICROSOFT_TENANT, default "common") registers Microsoft for both the authorization request and the token endpoint. [Setting up Microsoft sign-in](microsoft-oauth-setup.md) walks through registering an app with Microsoft to get that client ID. Google remains unavailable regardless of environment, since its refresh-token behavior needs separate handling.

The OAuth service generates a fresh 64-byte PKCE verifier, S256 challenge, and 32-byte state for each configured attempt, then opens the authorization URL only from the main process — there is no local network listener of any kind for this flow, on any port. The provider redirects the browser to its own registered redirect URI (Microsoft's native-client sentinel by default, or a caller-configured HTTPS address); the app never receives that redirect directly. Instead, the user copies the resulting address from the browser's address bar and pastes it back into the app, which validates it in the main process: the pasted value must parse as a URL, stay within a bounded length, match the exact registered redirect (origin and path), carry one timing-safe matching state, and carry exactly one bounded authorization code or provider error. Unparseable input, oversized input, wrong origin/path, wrong state, an access token appearing where only a code is expected, and an ambiguous result (more than one code, or a code alongside a provider error) are all rejected and reported by reason, with bounded retries before the attempt terminates as an error. The renderer receives only phase, provider, expiry, bounded failure reason, and provider availability—never the URL, state, verifier, code, access token, or refresh token.

A matching paste stops at `authorization-received`, and the class itself still calls no token endpoint and writes nothing to application state, history, notifications, or logs. The class optionally hands the code, PKCE verifier, and redirect URI to a single caller-supplied callback the moment a matching paste lands, before its state/verifier buffers are zeroed - the one seam where a real exchange can happen, entirely outside this file and never over IPC. In production that callback belongs to the main process alone and immediately exchanges the code for a token over a direct HTTPS request; nothing about that exchange reaches the renderer beyond a phase/failure snapshot with no token in it. Cancellation, five-minute timeout, browser-launch failure, provider denial/error, and repeated non-matching pastes all still reach explicit terminal states with the same cleanup, and none of them invoke the callback.

Microsoft's requested scopes also include the standard `openid`, `profile`, and `email` OpenID Connect scopes, which ask Microsoft to return an ID token alongside the access token. `src/main/oauth-id-token-claims.ts` reads that ID token's payload once, without checking its signature, to pull out only its `email` (or `preferred_username`) and `name` claims; every other claim, and the raw token string itself, is discarded immediately and never logged, returned, or persisted. Those two bounded, control-character-free values become the `accountHint` on the renderer-safe sign-in snapshot the moment a sign-in reaches `ready` - still no access token, refresh token, or code, and this is explicitly a prefill convenience, not a verified identity assertion: the account itself is still proven only by an actual IMAP/SMTP login. The Add Account form uses `accountHint` to fill its email and display-name fields exactly once each, and only while that specific field is still empty at the moment the hint arrives, so a value the user already typed - before, during, or after the browser round trip - is never overwritten, and both fields remain freely editable afterward.

### Windows token vault adapter

`src/main/oauth-token-vault.ts` provides a durable, main-process-only adapter around Electron `safeStorage` on Windows. A caller must supply a bounded, unique provider registration before initial save or rotation; production registers Microsoft only when a client ID is configured, and the revoker list stays empty for both providers (see Failure modes). Initial access and refresh values are independently encrypted before an atomic same-directory file replacement. A refresh rotates the encrypted access value, increments a generation, and either replaces a returned refresh value or preserves its existing ciphertext when a provider omits one. Tokens are limited to 8 KiB each, lifetimes to 24 hours, scopes to 50 unique bounded values, and the vault to 64 records in a 1 MiB document. Two read paths exist beyond the renderer-safe status/clear/revoke surface, and neither is reachable over IPC: `read(provider, accountKey)` returns one account's decrypted material for the main process's own mail connection, and `forgetAccount(provider, accountKey)` removes exactly that account's record without touching a sibling account on the same provider.

Renderer IPC exposes only Windows protection availability, bounded failure state, provider registration, record count, generation, expiry, and whether clear/revoke actions are currently available. It exposes no token, ciphertext, account key, scope name, provider error, or file path. Settings presents this status in an accessible bilingual live region. Provider-level local clear remains possible for orphaned ciphertext even when registration or Windows encryption later becomes unavailable. Revoke is enabled only for a registered main-process revoker; it decrypts inside the main process and removes the local records whether that provider call succeeds or fails. Active-file removal is not a secure-erasure claim, and no provider revoker ships in this build.

### Mock-only token lifecycle

`src/main/mock-oauth-token-lifecycle.ts` is an explicit local test/demo harness, not part of production initialization, `AppService`, preload, IPC, account state, or the visible demo workspace. `createDemoOAuthTokenLifecycle()` must be called deliberately by a demo harness; opening the normal local demo does not mint a token. The mock endpoint performs no network request and generates values labelled `mock-*`.

The harness models `idle → exchanging → active → expired/refreshing → active → revoking → revoked`, plus sanitized error states. Exchange requires a bounded mock authorization code and a 43–128-character base64url PKCE verifier. Refresh rotates both mock values and increments a renderer-safe generation counter. Revocation deletes the local encrypted record even when the mock provider revocation call fails. Public status contains only `mockOnly: true`, phase, expiry, scope count, generation, and a bounded failure code—never token material.

`EphemeralAesGcmOAuthTokenStorage` satisfies the mock encrypted-storage contract by keeping only AES-256-GCM ciphertext in a process-local map, binding ciphertext to its storage key with authenticated additional data, replacing/zeroing old blobs, and zeroing its random 256-bit key on disposal. It is deliberately non-durable and is **not** Windows credential storage or production at-rest evidence. The production Windows adapter is separate and never imports this mock endpoint or lifecycle.

Before either test or add can open a mail connection, a shared local preflight checks both endpoints. It blocks host fields containing schemes, paths, credentials, bracket notation, embedded ports, or certificate wildcards; blocks conventional implicit-TLS/STARTTLS port inversions; and rejects ports outside `1..65535`. IP literals and single-label/private names produce advisory certificate-identity warnings because they can be valid only when the server certificate policy covers the exact entered identity. Custom secure ports also remain advisory. The renderer presents the result live in an English, Hong Kong Cantonese, or bilingual status region, marks blocking fields with `aria-invalid`, promotes submitted errors to an assertive alert, focuses the first invalid field, and reports that no connection was started.

Live certificate inspection remains off until the user presses the incoming or outgoing inspection button. The main process then opens only a bounded diagnostic connection to the currently entered host and port: direct TLS for `tls`, or a fixed credential-free `STARTTLS` negotiation for IMAP/SMTP. One five-second deadline covers DNS, TCP, greeting, STARTTLS, and TLS handshake work; protocol responses cap at 16 KiB and certificate display caps at eight chain entries. No username, password, token, or mail content crosses this IPC or is sent to the server. Plain mode returns locally without opening a socket.

The result reports the runtime authorization decision, independent hostname match, TLS protocol/cipher, validity dates, public-key type/size, chain completion state, and short one-way certificate identifiers. Subject/issuer names, SAN entries, serial numbers, full fingerprints, PEM/DER bytes, and server greetings remain in the main process and are neither displayed nor persisted.

## Configuration

Incoming and outgoing settings each accept a host, port from 1 to 65535, `tls`, `starttls`, or explicit `plain` transport, and a username. Password authentication and, when Microsoft is configured, OAuth authentication can both test and persist a new connected account; POP3 saving remains blocked regardless of authentication mode. An account draft names its OAuth provider when authMode is oauth2, and the schema enforces exactly one credential source - a password with no provider, or a provider with no password. Inputs and provider IDs are length-bounded and schema-validated in the main process.

Conventional combinations are IMAP implicit TLS on `993`, IMAP STARTTLS on `143`, POP3 implicit TLS on `995`, POP3 STARTTLS on `110`, SMTP implicit TLS on `465`, and SMTP STARTTLS on `25`, `587`, or `2525`. The POP3 account test also permits an explicitly entered custom secure port after the existing advisory; it never permits plain transport. Other secure ports remain advisory. Explicit plain transport has no certificate identity check and does not protect credentials or message data, so it is unavailable to the POP3 test.

## Failure modes

- DNS discovery may time out, omit one service, or return stale records; manual configuration remains available.
- Conventional hostnames are guesses, not verified provider data.
- Connection tests can fail on DNS, proxy, firewall, certificate, protocol, authentication, or provider-policy errors.
- The local preflight cannot know whether a syntactically valid DNS name appears on the server certificate or whether a custom port speaks the selected protocol; the optional live inspection can observe the presented chain and runtime hostname/trust decision only after explicit action.
- Live inspection is point-in-time evidence from one bounded handshake. It does not perform OCSP/CRL revocation retrieval, certificate-transparency analysis, interception detection, pinning, provider login, or IMAP/SMTP interoperability testing.
- Password authentication may be disabled by a provider.
- Google OAuth cannot connect an account: it has no client registration and its authorization request does not yet request offline access, so registering a client ID for it today would produce a client that can sign in but never stay connected.
- Microsoft OAuth can connect an account once MATERIAL_EMAIL_MICROSOFT_CLIENT_ID is set, but no live Microsoft tenant has exercised sign-in, refresh, or IMAP/SMTP XOAUTH2 delivery yet - every scenario so far runs against a real local HTTP fixture speaking the token-endpoint protocol, not a real provider.
- Neither provider has a revoker wired in, so the Settings "Revoke and clear" action only ever clears local ciphertext; it cannot ask the provider to invalidate a token still held elsewhere.
- The mock token lifecycle proves local state transitions and ciphertext handling only. Mock exchange/refresh/revoke results are not provider responses, usable credentials, persistence proof, or interoperability evidence.
- The POP3 live test can fail on connection, TLS trust/identity, absent `STLS`/`UIDL`, authentication, timeout, oversized or malformed response, inconsistent message numbers, a duplicate/malformed UIDL, rejected command, cancellation, or early close. Errors are mapped to bounded public categories without copying server response text or credentials.
- Loopback integration proves the implemented implicit-TLS and STARTTLS transcripts, not compatibility with a public provider, proxy, firewall, IPv6-only service, unusual authentication policy, or a very large real mailbox.
- `QUIT` and closed sockets prove session cleanup for the test; they do not prove long-term leave-on-server behavior. Durable UIDL tracking, retention policy, deletion semantics, polling, folders, retrieval, account persistence, and complete synchronization remain absent.
- Local software can occupy an ephemeral callback port, block browser launch, or send invalid loopback requests. The state machine bounds and reports those cases but cannot make the local host trustworthy.
- Removing an account deletes its live local cache, drafts, outbox records, and pending operations but does not delete server data; retained append-only history can still describe the removed account and prior actions.

## Security considerations

Discovery performs DNS lookups only; it does not fetch or execute provider-hosted configuration code. Results remain advisory. The preflight runs locally and never logs or transmits entered settings. The live POP3 test crosses only the authenticated top-frame preload boundary, validates fixed password plus TLS/STARTTLS input, rejects CRLF/NUL credential injection, sends credentials only after TLS, never constructs deletion/retrieval commands, and returns no raw server-controlled text. Its cancellation channel accepts no arguments. There is no shipped POP3 demo mode, fixture UI, or alternate no-network POP3 endpoint; deterministic loopback servers exist only in the test suite. Live certificate inspection remains a separate credential-free IMAP/SMTP action. OAuth attempt secrets stay in the main process; the Windows vault sends only metadata through IPC; and the mock lifecycle remains isolated. Never log secrets or server-returned private data.

## Verification

The POP3 slice passes 4 transport integration tests plus 2 AppService boundary tests inside a 4-file / 28-test transport/AppService/IPC/security run. The deterministic test-only loopback servers cover implicit TLS, required STARTTLS with pre/post-upgrade `CAPA`, USER/PASS, STAT, bounded UIDL/LIST sampling, QUIT, silent-peer cancellation, socket cleanup, line/body caps, command-injection rejection, no retrieval/deletion commands, and output/error redaction. One real-Electron Settings scenario proves zero connection before the explicit click, a successful trusted loopback TLS test, no persisted credential/UIDL, disabled Connect, visible cancel/focus return, server-side close, bilingual semantics, and 760 × 560 layout. This is local loopback evidence, not public-provider interoperability, durable leave-on-server behavior, message retrieval, account persistence, or synchronization.

Focused Windows-vault verification passes 14 vault unit tests: the original 6 (registration gate, unavailable encryption, ciphertext-only persistence, access/refresh rotation, sanitized status, direct orphaned-record clear, successful revoke-and-clear, revoke-failure local clearing) plus per-account read/forget, a registered provider's non-secret client ID/token endpoint, and the loopback-only HTTP exception. `oauth-token-exchange.test.ts` (9 tests), `oauth-provider-config.test.ts` (5 tests), `app-service-oauth.test.ts` (9 tests), and 3 new `oauth-authorization.test.ts` cases together exercise the full Microsoft path - code exchange, refresh timing, vault rotation, test-without-consuming, add-consumes, restore-on-test-failure, and per-account forgetting - against a real local HTTP fixture speaking the token-endpoint protocol. Real-Electron Settings coverage still verifies bilingual status, disabled unregistered actions, no token input/key, and the 760 x 560 width bound. None of this is live provider exchange, revocation, mail authentication against a real Microsoft tenant, or interoperability evidence.
